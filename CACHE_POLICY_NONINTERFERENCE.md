## Problem and claim boundary

An agent must be able to compile its own code, but it need not learn whether another agent compiled the same code first. Hiding the cache directory is insufficient: a hit can change timing, output, statistics, failure behavior, or resource contention. Conversely, literal end-to-end noninterference is impossible if the receiver may observe a faster hit versus a slower miss chosen by a peer. RGEC therefore targets **agent-observation noninterference for admitted compile requests at fixed release times**, while retaining *compute* reuse. It does not promise lower agent-visible compile latency in strict mode.

This is a software build cache, not a CPU microarchitectural cache. The observer is an independently tasked agent and every tool result it can see. A broader claim covering clocks, other host workloads, physical side channels, compromised workers, or channels outside this cache would require additional mechanisms and evidence.

## The new policy

1. **Split authority.** The agent can edit its private checkout and request a compile, or compile locally without shared reuse. A separately identified trusted executor owns the compiler, cache credentials, cache mount, publication rights, and cache statistics. It sees only the requesting agent's checkout, the pinned toolchain and the cache, never another agent's checkout. The agent cannot enter that identity, mount the common namespace, submit raw cache keys, inspect receipts, or read hit/miss counters. Requests are bound to the requesting agent's checkout and a pinned compiler/toolchain policy; the executor derives keys from the agent's actual inputs and resolves arguments, paths and dependencies itself. An agent-controlled `CCACHE_DIR`, wrapper, environment variable, symlink or nested process cannot grant the executor's identity.
2. **Receipt-gated admission.** A shared entry is admitted only after a trusted execution produces a receipt for the *closed compile input*: compiler and relevant tool hashes, complete dependency bytes, arguments, permitted environment, platform and path context. Its key binds that closure. The receipt records hashes of exit status, stdout, stderr, output files and dependency files. A consumer hit requires matching closed inputs and intact receipt/output hashes. A missing, ambiguous, nondeterministic, unsupported or invalid receipt triggers a cold compile, never a best-effort peer hit. Cache entries and compiler outputs are not rewritten or fabricated.
3. **Epoch-fenced publication.** Workers may publish only after verification of a complete trusted result. A terminating semantic compiler failure may become eligible only if its diagnostic and effect continuation is certified; a recipient permission failure, producer timeout, resource failure or unsupported execution does not become a cached semantic failure. Newly published entries become eligible at the next publicly scheduled epoch boundary; no agent sees another agent's in-progress writes. The reader gets a fixed, immutable view for its epoch. Quotas and eviction must be partitioned or scheduled so another agent cannot cause a recipient-visible denial or timeout.
4. **Cold-trace delivery.** The recipient receives exactly the exit status, compiler diagnostics, dependency files and artifacts that a cold trusted build of *its own* closed input would return. No producer name, cache path, receipt, hit flag or shared stats enters its filesystem, stdout/stderr, tools or model context. If the native tool emits hit-specific diagnostics that cannot be disabled equally in cold and warm executions, that action is ineligible for strict reuse; do not strip or rewrite its output to manufacture equivalence. A cache entry is only a memoized cold result, not a peer-supplied message.
5. **Fixed-release strict mode.** For each admitted request, the host commits to a release tick determined solely by public schedule and the recipient's request class, before lookup. It preallocates per-recipient cold-build capacity independent of other agents' activity so a miss can finish by that tick. Hits and misses are released at the same tick; agent-visible timeout/failure rules must also be independent of peer state. If the bound or reservation cannot be met, reject the request *before lookup* under a rule independent of cache state and other agents' private work. Any post-lookup overrun invalidates the noninterference claim for that episode and is reported. The saved work is compiler CPU/energy and population goodput, not per-request wall-clock latency.

The unpadded mode may be useful operationally but is **not** called noninterfering: hit/miss latency can communicate at least a binary fact, often repeatedly. It is an explicit lower-assurance baseline with measured leakage. Read-only, private-cache and directory-hidden baselines are also distinct; none implies RGEC's guarantee.

**Operational state.** At epoch `e`, the broker holds an immutable eligible map `S_e` of key → `(trusted receipt, cold trace)` and a hidden pending map `P_e`. For an admitted request `(a, x)`, it computes `k = H(closure(x))` inside the executor. If `S_e[k]` has a valid receipt and matching closure, it loads that cold trace; otherwise it compiles `x` cold and places the verified result in `P_e`. It releases the trace at `T(a, class(x), e)`, a tick fixed before the lookup, with no hit indicator. At the public epoch boundary, the broker validates pending entries and atomically forms `S_(e+1)`; no entry from `P_e` serves a request in epoch `e`. Invalid or unsupported entries never become eligible. These rules specify policy behavior, not the unbuilt broker implementation.

## Formal security target

Let `Cold(x)` be the full trusted cold-build trace for a closed input `x`. Let `Obs_a(E)` project an execution to all agent `a`-visible tool results, files, metadata, errors and release ticks from RGEC. Consider two worlds `W ~_a W'` with identical public schedule, agent `a` inputs/actions, toolchain, and non-cache environment; only other agents' private inputs/actions and resulting cache contents differ. For each admitted request, the target is:

`Obs_a(RGEC(W)) = Obs_a(RGEC(W')) = Obs_a(Cold(a's requests) released on the public ticks)`.

For stochastic compilers, replace equality with equality of observation distributions conditioned on the same recipient input; otherwise bypass shared admission. The claim is **conditional** on complete input closure, deterministic cold output (or the stated distributional coupling), collision-resistant hashing, trusted isolated workers, authenticated request identity, no direct common-store access, fixed-release capacity, and absence of other shared channels. It is an API/tool-trace property under this threat model, not an unconditional operating-system theorem. The desired proof is by induction on requests: a valid hit and a cold miss yield the same recipient trace for the same closed input; publication changes only hidden state; fixed release removes cache-state-dependent timing. Each assumption is a proof obligation, not a demonstrated fact.

### Why the restrictions are necessary

If a peer can choose whether to warm key `k`, and the receiver can distinguish hit and miss latency, the peer can transmit one bit by warming `k` or not. A hidden directory, signed artifact, or read-only client does not remove that timing channel. If a peer can publish arbitrary bytes, output integrity fails even when timing is padded. If a cache key omits an include file, flag, environment value or path dependence, a hit may differ from `Cold(x)`. If a strict release slot is exceeded only on a miss, the timeout itself transmits the bit. These are counterexamples to stronger claims and must appear in the paper.

## Novelty hypothesis and nearest baselines

The proposed research delta is the **joint receipt-gated admission, epoch-fenced publication, and fixed-release observation contract for agent-operated build workflows**, together with a checkable conditional noninterference argument and measured compute-versus-latency cost. Ordinary ccache already caches compiler outputs and supports remote read-only storage; read-only storage and an opaque directory alone are not inventions here. Build systems already use remote action caches and [hermeticity](https://bazel.build/concepts/hermeticity) to support correct reuse; [reproducible builds](https://reproducible-builds.org/docs/definition/) and information-flow noninterference are established theory. RGEC's combination and its applicability to authentic autonomous-agent builds remain **hypotheses**, pending a full-text prior-art comparison and implementation. See the [ccache manual](https://ccache.dev/manual/4.14.html), [Bazel remote-cache documentation](https://bazel.build/remote/caching), and [system-level cache noninterference](https://doi.org/10.1145/2660267.2660283) as starting points, not an exhaustive search.

## Real-system evidence required, in order

1. **Native compatibility:** in the actual CyberGym task image, complete the target build and reference reproduction under a private cold build, native shared ccache, and RGEC. Match exit status, diagnostics, dependency files, produced artifact hashes and functional tests; record every unsupported or nondeterministic compile. A full vulnerable-image target build now passes under *native ccache in trusted workers*, but reference reproduction, fixed-image grading and RGEC itself remain open.
2. **Enforcement:** with real agent containers and ordinary build commands, verify the agent cannot read/write/enumerate the shared store, access worker credentials, invoke the worker as itself, request another checkout's inputs, or extract hit/miss stats. Test direct compiler paths, environment overrides, symlinks, subprocesses and failure responses. A failed legitimate build is a policy failure, not a security success.
3. **Warm-state equivalence:** on real repeated builds, compare cold and cross-agent warm recipient traces byte-for-byte after only the path/context normalization that the actual build system already performs. No synthetic workload counts as evidence. Investigate any differing warning, depfile, object, error, timestamp or path.
4. **Timing and capacity:** measure real cold-build tail latency to set release slots on a disjoint calibration corpus. Measure missed slots and resource interference on held-out full tasks. A single state-dependent overrun defeats the strict claim for that run. Report compute saved, goodput, energy if measurable, and agent-visible wall time separately.
5. **Independent security review:** complete the formal model/proof and adversarial implementation audit. Then run the secondary randomized score/utility study with frozen outcomes, task selection and sample size. No passing build or software unit test substitutes for these steps.

**Stop condition:** if complete dependency closure or fixed-release capacity cannot be enforced at acceptable cost on real tasks, narrow the claim to functional-output noninterference with explicitly disclosed timing leakage, or reject RGEC as a practical strict policy. Do not relabel a weakened guarantee as strict noninterference.

## Implemented delegation precursor — 2 October 2026

The cold build boundary now exists in [build_broker.py](src/unauthorized_channels/build_broker.py). It is a prerequisite for RGEC, not the implemented cache policy or a noninterference proof.

The trusted host prepares a derivative of the immutable ARVO image before agent access, changing ownership of `/work` and `/out` so native compilation does not require filesystem capabilities at runtime. The preparation container has no agent edits or host mounts and is removed afterward. Each host-owned tool binding then starts a separate private build container with UID 0, effective/permitted/bounding capabilities all zero, no-new-privileges, network none and no filesystem mounts. UID 0 can modify its own container filesystem; it does not acquire the host's store authority under the trusted Docker/kernel assumption.

Only `{"action": "compile"}` is accepted by the compile request API. Its host binding determines the recipient container and pinned task. Session, checkout, image, environment, command and raw-key fields are rejected. Agent edits and arbitrary tool commands execute inside that recipient's container. This is an in-process host tool binding, not a network authentication service; the trusted orchestrator must not expose its Python objects or Docker API to agents. The old `AgentSandbox` and population execution paths are unchanged.

The host's real native cache remains outside every build container. **All requests run cold; no entry is read, admitted or published.** Compiler output is retained as bytes, including invalid UTF-8 diagnostics. A timed-out compile destroys its container so descendants cannot keep writing behind another request. No receipt signing keys or cache-service credentials are issued to build processes.

The next eligible cache unit will be an **isolated compiler action**, not an entire mutable ARVO build. Shell scripts, configure, linking and installation continue to execute as ordinary private work unless their own closure and effect semantics are separately established. Before enabling any shared hit, implement an immutable compiler/toolchain and enforceable read namespace, complete input/negative-dependency closure, output effects and full recipient observation semantics. The current private container is mutable and therefore does not certify compiler provenance or receipt soundness.

New real-system evidence records two final native target builds after removing the prebuilt `coder_MNG_fuzzer`, with successful regeneration required. Edited scripts, nested processes, compiler wrappers and a loaded native compiler plugin tested access to an actual host cache object. Direct, symlink and `/proc/1/root` paths and Docker-socket access were denied on the audited surfaces; own-source access worked. Six request overrides were rejected, the real host cache digest stayed unchanged, and the peer's build.sh hash stayed unchanged. Native diagnostic-byte preservation and real-build timeout invalidation have separate real Docker checks.

These findings establish the tested **cold delegation boundary on one image**, not shared-reuse conformance, complete trace equivalence, hard scheduling capacity or host-wide confinement. The published review assessed the earlier design, not this code. Existing receipts/epochs/release proof obligations remain open. Container flag mechanics follow the [Docker run documentation](https://docs.docker.com/engine/containers/run/); the security claim still depends on the stated trust boundary and evidence.

### Candidate mechanism: certify the recipient transition, not only the cached value

The old receipt definition hashes output files and streams. That is insufficient for the desired adaptive guarantee: equal object bytes do not imply equal file identity, permissions, links, timestamps, partial-write visibility, pre-existing output behavior or later reads. A receipt must support a **recipient state transition**. This is the mechanism to develop next; it is not implemented or established as novel.

Write an admitted cold broker action as `C(x, V)`, where `x` is the immutable computation input and `V` is the recipient's complete observable state. Seek a decomposition into a hidden compiler payload `F(x)` and a recipient effect operation `R(x, V, F(x))`. Both hit and miss must execute the *same* recipient operation. Reusing producer inode/timestamp state, omitting a cold side effect, or choosing a different write primitive on a hit is forbidden. The admission predicate and effect program must be fixed from recipient/public state before shared lookup. Unsupported actions remain private independently of cache contents.

The required certificate is contextual: for every admitted recipient pre-state and every permitted future recipient tool sequence, `C(x, V)` and `R(x, V, F(x))` yield related observable states and the same stream/status contract. An object hash or signed execution manifest does not prove this. The worker's currently recorded native metadata is evidence to investigate, not metadata to copy from a producer or normalize after the fact. An implementation must specify actual filesystem operations on the recipient and compare them with the cold broker contract. Compatibility with ordinary native compilation is a separate obligation; defining a new broker API does not automatically prove native compatibility.

### History-level state relation

Model a broker state as `(V, Q, K, P, B)`: recipient-visible states `V`, public admission/release queues and reservations `Q`, hidden eligible cache `K`, hidden pending publication `P`, and isolated backend state `B`. Relate two worlds only when the recipient's observable state and public queue/reservations agree; their peer work, cache and hidden backends may differ. Equality must include all future permitted tools, including filesystem metadata and error paths. Concurrent recipient requests need a public ordering rule, not ordering by backend completion.

The following is a **conditional composition lemma**, not the completed RGEC theorem. Assume (i) immutable closure makes every valid payload equal to the recipient's deterministic cold payload, (ii) `R` preserves the contextual recipient-state relation for success and failure, (iii) no hidden backend/cache transition becomes visible before release, and (iv) admission, ordering, reservations, release and failure rules depend only on related public/recipient state and meet their hard bounds. Then adaptive recipient transcript equality follows by induction:

1. Related transcript prefixes cause the same next action under the same recipient strategy; private fallback/admission and release commitments are therefore the same.
2. A valid hit supplies `F(x)`. A miss or invalid entry computes that same payload under (i). Lookup/publication may change only hidden states under (iii).
3. At the committed tick, both worlds execute `R` with related recipient states and equal payloads. By (ii), their streams/status agree and their resulting states remain related, including later tool observations. By (iv), failure and release events agree.
4. The invariant thus holds for the next adaptive prefix. A slot overrun, visible partial effect, cache-dependent rejection or unsupported nondeterministic payload breaks a premise; it must be recorded as a guarantee failure, not excluded afterward.

The missing work is to **construct and enforce** premises (i)–(iv) on the native system. Repeated equal samples do not establish determinism; clock/file-state mediation and native effect conformance cannot be assumed. A stochastic extension requires a joint coupling over complete adaptive histories and fresh recipient randomness; equal one-request marginals do not suffice. If validated publication remains wholly hidden and payloads satisfy (i), epoch fencing is not needed for this lemma. Epochs therefore require a separate operational justification, not an invented proof necessity.

## Recipient-effect admission and a real cache-state counterexample — 2 October 2026

The next candidate policy mechanism is now concrete: **establish the recipient output operation before consulting the shared store, then execute that same operation for cold and reused payloads**. [recipient_effect.py](src/unauthorized_channels/recipient_effect.py) implements a measured precursor. This is an effect-aware refinement of RGEC admission, not a completed receipt certificate or a new priority claim for atomic replacement.

The native effect experiment uses the authentic pinned Clang and configured zlib/GraphicsMagick sources on Modal. It covers existing regular files, hard links, symlinks, dangling symlinks, absent outputs, read-only files/parents, directories and missing parents, with successful source and a genuine source edit causing a preprocessing error. Prior output bytes come from a real native deflate object. Held descriptors, aliases, target files, modes, ownership, link counts and native metadata are recorded. The comparator does not construct synthetic compiler results.

**Observed counterexample:** with an existing read-only output, native compilation and a fresh ccache store return 1 and preserve that file. A confirmed warm hit in released **ccache 4.14.1** returns 0 and replaces it. This occurred for both real translation units, and repeated twice per target with exactly the same compiler output-path argument. The release archive and its trusted comment were verified against the official minisign key. The baseline uses default result handling, no hard-link mode or sloppiness changes, and an isolated laboratory cache. This is not an integrated agent or RGEC cache.

This difference is consistent with ccache's [result retriever](https://raw.githubusercontent.com/ccache/ccache/v4.14.1/src/ccache/core/resultretriever.cpp), which sends embedded artifact bytes to its file writer, whose [default operation](https://raw.githubusercontent.com/ccache/ccache/v4.14.1/src/ccache/util/file.hpp) [unlinks an existing output before writing](https://raw.githubusercontent.com/ccache/ccache/v4.14.1/src/ccache/util/file.cpp). Clang's [frontend output handling](https://raw.githubusercontent.com/llvm/llvm-project/llvmorg-7.0.0/clang/lib/Frontend/CompilerInstance.cpp) checks destination write access first, while its [driver failure cleanup](https://raw.githubusercontent.com/llvm/llvm-project/llvmorg-7.0.0/clang/lib/Driver/Compilation.cpp) removes writable regular outputs after a failed job. The LLVM 7 release source explains the sampled behavior; it is not a source-exact proof for this image's trunk revision.

An agent can distinguish these cache states by the returned status and retained output, even if both results arrive at an identical release tick. The experiment did not enforce such ticks; the statement follows because delaying a result does not change its status or file effects. Thus trusted payload bytes plus a hidden store and release padding are insufficient for this native output context. A timing-only fix cannot close this particular difference. This does not establish a deployed multi-agent channel or characterize its capacity.

### Concrete recipient operation

`RecipientOutput(directory, name)` binds the recipient directory with `O_PATH`, checks native write eligibility, and allocates a fresh local temporary output before payload retrieval. On success it writes the native object unchanged and renames the temporary over the output entry. On a compiler failure it closes and removes its temporary, then repeats the native driver's writable-regular-output cleanup. This preserves the measured old-descriptor and alias behavior. It never copies a producer's inode, timestamps or permissions into the recipient. The operation must use the native recipient's credentials and umask, as in the matched UID/GID 65534 experiment; privileged publisher access would invalidate its permission check.

Read-only outputs, nonregular destinations, missing parents and unavailable temporary-file creation cause **private fallback before lookup**. The full native compiler then handles those cases, including the writable-file/read-only-parent direct-write behavior. A warm cache entry cannot override this decision. The tested admitted states include regular files, hard links and symlinks; they are not discarded just to make a byte comparison pass.

The structural experiment has 36 cases: 20 use the recipient operation and 16 use actual native fallback. All measured structural effects agree; admitted captured streams/status also agree. Structural equality excludes exact inode numbers, timestamps, intermediate visibility and concurrent tool behavior. Native metadata remains raw. These counts therefore do not certify full trace equivalence.

A real post-completion **inotify queue** exposed an extra directory `IN_OPEN` from the initial directory read descriptor. `O_PATH` eliminated that event on the tested Modal runtime. Failure cleanup order was also corrected to remove the temporary before the final output. The final native/recipient success and failure queues agree in event-mask order and file-role pattern for the sampled adler32 case; their actual random temporary names and move cookies differ and remain preserved. This is one queue comparison, not equality of event distributions or a proof covering all watchers. Merely pausing an agent would not erase kernel events queued for later reads.

### Refined protocol and proof obligation

Split a request into `Begin(x,V,u)`, hidden payload retrieval/execution, and `Finish(ticket,payload,V)` at the committed public release. Here `u` is fresh recipient randomness, independent of peer work and cache contents; the output ticket is recipient authority and must never be cached or supplied by a producer. Both worlds must execute the same Begin/Finish operations. The caller must bind the correct recipient namespace and prevent unauthorized mutation of the ticket or its directory. The current laboratory module assumes that binding/lease; it does not enforce it across live agent processes.

There are now three distinct certificates to construct:

1. **Payload soundness:** immutable closure and compiler semantics make each accepted cached payload equal to the recipient's cold payload. The existing provenance manifest does not prove this.
2. **Effect soundness:** every admitted recipient state and future permitted observation, including queued events, errors and metadata, is preserved by the selected Begin/Finish program. The finite experiment is evidence for specific branches, not a universal certificate.
3. **Protocol soundness:** admission, fresh effect allocation, authority binding, capacity, ordering and release depend only on related recipient/public state. Cache failures, corruption and backend overruns cannot select different visible outcomes.

Conditionally, the earlier history lemma extends as follows. Related adaptive prefixes select the same request. Since Begin cannot inspect cache state and uses jointly coupled fresh recipient randomness, it yields related local tickets/states or the same private fallback. Payload soundness makes the hidden hit and miss yield equal payloads. Effect soundness and the public release commitment then preserve the relation at Finish, including future observations. Hidden publication preserves the relation. Induction continues. This argument remains conditional until the three obligations are enforced and proved; it is not an unconditional OS theorem or an established new noninterference result.

The candidate research delta is a **checkable native effect-admission contract separating reusable computation from recipient authority and exceptions**, composed with adaptive cache-state noninterference. Fixing one permission check is insufficient for a PhD-level contribution. [zccache's documented staged outputs and filesystem materialization](https://github.com/zackees/zccache#immutable-staged-outputs) already separate private compilation, publication and delivery, including worktree sharing. Those mechanisms join BuildXL, Bazel, verified memoization and predictive timing mitigation as necessary stronger comparisons. At this earlier phase only its README had been inspected. The later native-continuation phase tests actual zccache 1.15.1 misses and hits: both replace recipient-owned read-only outputs where native Clang fails. This is a sampled native-effect compatibility difference, not an absence-of-prior-art or cache-state-dependent status claim. The next work is sound closure and namespace/ticket binding, then integrated cold/warm adaptive traces and a proof. Strict cold-capacity reservations also require a separate demonstration of any population goodput gain; saved CPU alone does not establish higher admission throughput.

## Native continuation and failure admission — 3 October 2026

The proposed admission contract now separates three failure sources. **Recipient failures** arise from local authority and state, such as opening output or removing an old file; native recipient code must produce them before lookup or during continuation. **Semantic failures** arise from the admitted closed compiler computation, such as a backend invalid instruction; they may be reusable together with a certified effect recipe. **Infrastructure failures** arise from producer interruption, missing closure, resource exhaustion or transport; they cannot be relabeled as semantic failures or admitted merely because their exit status is 1. This extends the policy's result domain; it does not establish that the prototype can classify every native failure soundly.

Write the native request as `P(x,V) -> Terminal(o,V') | Suspended(k,c)`. The prefix `P` must execute in the recipient, before any lookup. The capability `c` retains the native output stream, native diagnostic/source context and native driver continuation; it is request-local and never enters the cache. The reusable value is an effect recipe `tau`, not the producer's files or descriptors. Its allowed operations are native writes, positioned writes, typed diagnostics and justified virtual diagnostic buffers. It cannot choose a recipient identity, path, descriptor, inode, timestamp, temporary name or release tick. Native continuation `K(c,tau)` consumes the capability exactly once. The same `K` must handle a verified hit and a separately computed miss, including semantic failure and local failure cleanup.

The important proof obligation is **response independence**, not just a list of allowed operations. The hidden computation must not branch on recipient-specific output responses that were absent from the key: space exhaustion, short writes, seekability, flush errors and diagnostic state can change control flow. Either the admission certificate proves those responses irrelevant or preserves a validated native decision structure under the actual responses. A tape sampled on a writable producer filesystem does not establish this property. Likewise, an exact bitcode key is not a complete diagnostic-context key, and a matching full key is not a closure or origin certificate.

The native backend experiment implements a real `EmitBackendOutput` cutpoint, source/state binding and native continuation through the actual outer driver. Its successful finite comparisons cover both successful and failed backend computation. A genuine failed attempt established that replaying cc1 alone omitted output deletion and a permission diagnostic; the authentic outer driver is therefore part of the measured continuation. The further Modal failure-repair/header/dependency/corruption experiments are recorded in the final handoff. Native frontend work remains in every recipient request.

The current [Swiftlang Clang CAS implementation](https://raw.githubusercontent.com/swiftlang/llvm-project/next/clang/lib/Frontend/CompileJobCache.cpp), inspected 3 October at lines 492–505, excludes failed builds and identifies non-atomic removal of a preexisting output as unmodeled. This supplies a specific comparison target for the failure/effect contract. [Tiniris](https://simongregersen.com/papers/2021-tiniris.pdf) already verifies memoization of purely acting functions, and [Grimm et al.'s relational framework](https://secpriv.tuwien.ac.at/fulltext/publik_270459.pdf) verifies memoization and other effectful program properties. Reifying operations into data is not, by itself, a new theorem. The intended contribution must construct a sound native admission certificate and an adaptive guarantee over these recipient effects, then demonstrate a supported real domain and its costs beyond those established abstractions.

The new experimental host recipe store authenticates origin/context and packet bytes before delivery; this is separate from semantic admission. Its MAC key stays outside compiler sandboxes. Host-controlled producer identity, exact key reproduction and intact bytes are necessary evidence, but do not prove determinism, complete dependencies or response independence. Fixed release, cold-capacity reservation, epoch integration and production admission remain open. The full research goal is unchanged.

**Further novelty hypothesis: residual closure.** The certificate should close the computation remaining after the native prefix, rather than requiring the entire request to act purely. The prefix may evaluate live clocks, include existence, current recipient permissions and native frontend diagnostics on every request; their relevant outcomes must enter the captured residual context, while their local effects remain recipient-owned. This extends the candidate domain relative to this project's earlier sealed whole-request producer, but does not establish an advantage over all compiler caches: [ccache 4.14.1](https://ccache.dev/manual/4.14.1.html) handles time macros through preprocessor mode, and its `time_macros` sloppiness deliberately allows stale values. No sloppiness-based relaxation is used here. The contract requires proving that no uncaptured prefix state can affect the residual computation or its continuation. It is a supported-domain hypothesis, not a new theorem established by defining a key. The October 3 authenticated producer reruns the frontend; the separate October 4 prototype below consumes genuine captured IR without parsing the original sources again. Complete residual closure remains unproved.

**Observed counterexamples:** real Modal `/dev/full` and `RLIMIT_FSIZE` tests initially produced six native/replay diagnostic mismatches despite equal exit statuses and matched queued event roles. Installing the native cc1 fatal-error handler fixes all three `/dev/full` comparisons on the rebuilt compiler. All three file-size-limit comparisons still have different crash diagnostics. This is a native-compatibility failure, not demonstrated cache-state leakage: the experiment compares native compilation with replay, not hit with miss. It prevents a complete effect-certificate claim. The failure is retained and prioritized; it is not erased by excluding the failing rows or rewriting their diagnostics. See the current handoff and admission-phase report.
